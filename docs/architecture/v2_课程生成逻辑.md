## 1. 目标与范围

本文定义 V2 从用户提出学习目标，到课程规划、章节任务规划、瀑布式学习、流内答疑、理解检查和章节完成的完整业务流程与工程契约。

本文用于指导开发实现，而不是描述当前代码已经具备的能力。实现必须按 P0～P5 分阶段推进，不得把后续阶段能力偷偷并入前一阶段。

V2 的核心运行模型是：

```text
Course Blueprint（稳定路线）
  → Chapter Plan（本章任务骨架）
  → Task Content（当前任务即时生成）
  → Learning Stream（用户实际经历）
  → Learning Evidence（理解证据）
  → Next Teaching Action（下一步教学动作）
```

## 2. 端到端业务流程

## 2.1 创建课程

```text
用户输入主题和目标
  ↓
Outline：解构意图、起点、边界和成功标准
  ↓（信息不足时最多澄清 3 次）
Course Blueprint
  ↓
TOC：按目标簇组织章节及依赖
  ↓
课程目录可展示
  ↓
后台预热第一章 Chapter Plan
```

### Outline 应解决的问题

1. 用户真正想解决什么问题？
2. 目标属于概念理解、技能掌握、问题解决还是快速复习？（如未来需要“决策支持”等新意图类型，必须同时补充对应的教学模式和检查设计，不能只加枚举值。）
3. 用户将在什么场景使用所学内容？
4. 用户已有基础、明确排除项和时间约束是什么？
5. 完成课程后，用户应能做出什么可观察行为？

Outline 不应只输出“学习方向”和“预计水平”，而应建立课程的业务契约。

### Course Blueprint 建议结构

```ts
interface CourseBlueprintV2 {
  blueprintId: string;
  protocolVersion: 2;
  topic: string;
  intentType:
    | 'conceptual_understanding'
    | 'skill_mastery'

    | 'fast_review';
  targetScenario: string;
  learnerStartingPoint: {
    estimatedLevel: 'beginner' | 'intermediate' | 'advanced';

  };
  courseObjectives: LearningObjective[];
  successCriteria: string[];
  chapters: ChapterDefinition[];
  createdAt: number;
  promptVersion: string;
  modelVersion: string;
}

interface LearningObjective {
  objectiveId: string;
  description: string;
  observableOutcome: string;
  importance: 'core' | 'supporting' | 'optional';
  evidenceRequirement: 'exposure' | 'self_report' | 'demonstration';
  conceptKeys: string[];
}

interface ChapterDefinition {
  chapterId: string;
  index: number;
  title: string;
  objectiveIds: string[];
  prerequisites: string[];
  teachingGoal: string;
  completionCriteria: string[];
}
```

### Blueprint 校验

生成结果保存前必须通过程序校验：

- ID 唯一且引用存在。
- 至少有一个核心课程目标。
- 每章至少绑定一个目标。
- 所有核心目标至少被一个章节覆盖。
- 章节依赖无环。
- 排除项没有被列为必学目标。
- `observableOutcome` 是行为描述，不是“了解、熟悉、掌握”等空泛词。

失败时优先让模型修复具体字段，最多重试一次；仍失败则返回可重试错误，不能静默拼装低质量课程。

## 2.2 生成章节计划

Chapter Plan 把本章目标拆成有限的短任务，但不预先生成整章正文。

```text
Chapter Definition
+ Course Blueprint 摘要
+ 相关长期画像
+ 已完成章节摘要
  ↓
Chapter Planner
  ↓
Chapter Plan（3～7 个任务骨架）
```

### Chapter Plan 结构

```ts
interface ChapterPlan {
  chapterId: string;
  planId: string;
  planVersion: number;
  objectiveIds: string[];
  tasks: PlannedTask[];
  status: 'draft' | 'active' | 'completed' | 'superseded';
  createdAt: number;
  updatedAt: number;
  generationMeta: GenerationMeta;
}

interface PlannedTask {
  taskId: string;
  order: number;
  title: string;
  objectiveId: string;
  taskGoal: string;
  observableOutcome: string;
  conceptKeys: string[];
  prerequisiteTaskIds: string[];
  teachingPattern:
    | 'explain'
    | 'worked_example'
    | 'compare'
    | 'process'
    | 'derive'
    | 'practice'
    | 'case_analysis'
    | 'recap';
  expectedMinutes: number;
  evidencePolicy: 'none' | 'self_report' | 'checkpoint';
  origin: 'initial' | 'remediation' | 'extension' | 'user_requested';
  status: 'planned' | 'prefetched' | 'active' | 'completed' | 'skipped';
}
```

### 任务规划约束

- 每章通常 3～7 个任务；超出必须给出明确业务理由。
- 每个任务只承担一个主要目标。
- 每个核心目标至少有一个对应任务。
- 任务预计时长一般为 1～3 分钟。
- 先建立必要心智模型，再进入应用和迁移。
- 已确认掌握的基础可压缩，但不能仅凭画像直接跳过高风险前置知识。
- Checkpoint 只放在关键目标或必要边界处，不要求每任务都有。
- 最后一个任务负责本章目标整合，但不提前教授下一章正文。

### 计划质量校验

```ts
interface PlanValidationResult {
  valid: boolean;
  errors: Array<{
    code: string;
    taskId?: string;
    message: string;
  }>;
  warnings: Array<{
    code: string;
    taskId?: string;
    message: string;
  }>;
}
```

必须拦截：

- 目标覆盖缺失。
- 重复任务。
- 任务依赖指向不存在的任务。
- 循环依赖。
- Checkpoint 没有关联目标。
- 全章任务都使用同一种教学模式。
- 任务描述只是章节标题的改写。

## 2.3 进入章节与恢复

进入学习页时按以下优先级处理：

```text
1. 读取 NodeLessonV2 / ChapterRuntimeState
2. 已完成 → 展示完整学习流和章节结果
3. 有未完成任务 → 恢复任务与滚动锚点
4. 有 Chapter Plan 但无内容 → 生成当前任务
5. 无 Chapter Plan → 生成计划，再生成 Task 1
```

页面不能因为后台恢复或预取而覆盖已展示内容。任何异步结果写入前必须检查：

- `courseId`
- `chapterId`
- `planId`
- `planVersion`
- `taskId`
- `requestId`

不匹配的结果标记为废弃，不进入学习流。

## 2.4 任务生成与展示

任务内容不是一个大字符串，而是由结构化内容块组成。

```ts
interface GeneratedTask {
  taskId: string;
  planVersion: number;
  title: string;
  blocks: LearningContentBlock[];
  boundaryPrompt: TaskBoundaryPrompt;
  sourceRefs?: SourceRef[];
  generationMeta: GenerationMeta;
}

type LearningContentBlock =
  | MarkdownBlock
  | KeyPointBlock
  | ExampleBlock
  | ComparisonBlock
  | ProcessBlock
  | VisualizationBlock
  | CodeBlock
  | ReflectionBlock;
```

建议第一版保留有限块类型，避免协议过早复杂化：

```ts
interface MarkdownBlock {
  type: 'markdown';
  blockId: string;
  markdown: string;
}

interface KeyPointBlock {
  type: 'key_point';
  blockId: string;
  title?: string;
  points: string[];
}

interface ExampleBlock {
  type: 'example';
  blockId: string;
  title: string;
  context: string;
  content: string;
  takeaway: string;
}

interface ComparisonBlock {
  type: 'comparison';
  blockId: string;
  columns: string[];
  rows: string[][];
}
```

### 内容质量要求

每个任务应做到：

1. 首段快速建立动机或问题，不重复课程背景。
2. 只讲完成当前任务所需内容。
3. 新术语在首次出现时解释。
4. 案例与目标场景相关，不为生动而编造事实。
5. 结尾形成一个可带走的判断、步骤或心智模型。
6. 内容能支持任务声明的 `observableOutcome`。
7. 默认控制长度；需要深入时由用户触发或计划明确要求。

### 任务边界

任务完成后进入 `awaiting_user`，页面显示：

- 主操作：`继续学习`
- 辅助操作：`我有问题`
- 辅助操作：`再举个例子`
- 可选：`换种讲法`

如果该任务绑定 Checkpoint，则先展示检查；完成检查或选择稍后再试后才能继续。是否允许跳过由课程策略决定，并记录为“未取得证据”，而不是失败。

## 2.5 累积式 Learning Stream

`LearningStreamItem` 是用户实际学习经历的持久记录。

```ts
type LearningStreamItem =
  | TaskContentItem
  | UserQuestionItem
  | TutorAnswerItem
  | SupplementalItem
  | CheckpointItem
  | CheckpointResultItem
  | TaskTransitionItem
  | ChapterRecapItem
  | SystemNoticeItem;

interface StreamItemBase {
  itemId: string;
  type: string;
  chapterId: string;
  taskId?: string;
  planVersion: number;
  createdAt: number;
  status: 'pending' | 'streaming' | 'complete' | 'failed' | 'superseded';
}
```

关键规则：

- 已经向用户展示并完成的 Item 只能追加修正说明，不能被后台静默删除或改写。
- 流式生成中的 Item 可以增量更新，完成后固化。
- 失败 Item 保留失败状态，并允许原地重试。
- 重试生成新 Item 或新 attempt，不覆盖原始请求记录。
- Stream 顺序使用明确的 `sequence` 或服务端排序键，不能依赖数组写入竞态。
- V1 的 cards/questions 不需要强行转换成 V2 Stream；迁移期按协议版本选择渲染器。

## 2.6 流内提问

用户提问不打开独立于课程的对话世界，而是在当前任务下追加问题和回答。

### 2.6.1 流式生成中提问的行为定义

底部输入框常驻，意味着用户可能在任务内容仍在流式追加（章节状态 `learning`）时提交问题。该场景行为必须确定，前端不得自行发明：

```text
用户在 learning 状态提交问题
  ↓
输入框立即可用性反馈：问题以 pending 状态追加为 UserQuestionItem
  ↓
当前正在流式输出的内容块继续完成（不中断当前任务生成）
  ↓
当前任务剩余块暂停生成，任务标记为 partial_paused
  ↓
Tutor 处理该问题并流式回答
  ↓
回答完成后展示"继续本节内容"入口
  ↓
用户继续 → 恢复该任务剩余块生成（同一 taskId 新 attempt，衔接已展示内容）
```

规则：

- 问题提交永远不丢弃：无论当前处于什么状态，`UserQuestionItem` 立即入流。
- 中断粒度是内容块，不是字符：正在输出的块完整结束后才切换到回答，避免出现半句话。
- `partial_paused` 的任务恢复时从未完成的块继续，不重新生成已展示的块。
- 若问题在任务边界（`awaiting_user`）提交，则走标准答疑流程，无需暂停逻辑。
- P2 第一版可将该场景简化为"排队"：问题入流但提示"本节讲完后回答"，任务完成后自动触发回答。选择"排队"还是"块间打断"由 P2 实现时依据任务实际时长决定——任务超过 1 分钟时排队体验不可接受，必须实现块间打断。

### 2.6.2 请求上下文

Tutor 请求只发送必要信息：

- 当前课程目标摘要。
- 本章目标。
- 当前任务目标。
- 当前任务已展示内容摘要或相关块。
- 本章最近若干条问题与回答。
- 与当前概念相关的学习证据。
- 用户问题。

不应重复发送整门课程、全量历史和已经凝结为摘要的旧消息。

### 教学动作

P2 只开放低风险动作：

```ts
type TutorAction =
  | {
      type: 'answer_inline';
      reasonCode: 'LOCAL_QUESTION';
    }
  | {
      type: 'expand_current';
      reasonCode: 'NEEDS_EXAMPLE' | 'NEEDS_MORE_DETAIL';
    }
  | {
      type: 'switch_explanation';
      reasonCode: 'EXPLANATION_MISMATCH';
    }
  | {
      type: 'proceed';
      reasonCode: 'USER_READY';
    };
```

P3 新增：

```ts
| { type: 'remediate_here'; reasonCode: 'LOCAL_MISCONCEPTION' }
| { type: 'insert_remediation_task'; reasonCode: 'PREREQUISITE_GAP' }
```

P4 才新增：

```ts
| { type: 'compress_remaining'; reasonCode: 'STRONG_PRIOR_EVIDENCE' }
| { type: 'deepen_remaining'; reasonCode: 'USER_REQUESTED_DEPTH' }
| { type: 'reorder_remaining'; reasonCode: 'DEPENDENCY_DISCOVERED' }
```

### Tutor 输出契约

```ts
interface TutorDecision {
  action: TutorAction;
  confidence: number;
  answer?: LearningContentBlock[];
  candidateSignals: CandidateLearningSignal[];
  planPatch?: ChapterPlanPatch;
}
```

禁止要求或保存模型详细思维过程。可观测性使用 `reasonCode`、`confidence`、输入摘要、动作和结果。

### 回答原则

- 先直接回应用户问题，再决定是否补背景。
- 优先给最小充分帮助，不立即倾倒完整答案或整章内容。
- 如果用户正在完成微实践，先给提示而非替用户完成。
- 明确回答与当前主线的关系。
- 回答结束后恢复继续入口。
- 与课程无关的问题可简短回答并引导回主线，不能擅自改课程目标。

## 2.7 理解检查与补救

Checkpoint 的目的是取得目标证据，不是增加题量。

### Checkpoint 类型

```ts
type CheckpointKind =
  | 'scenario_choice'
  | 'self_explanation'
  | 'sequence'
  | 'micro_practice'
  | 'error_diagnosis';

interface CheckpointDefinition {
  checkpointId: string;
  objectiveId: string;
  taskId: string;
  conceptKeys: string[];
  kind: CheckpointKind;
  prompt: string;
  options?: Array<{ id: string; text: string }>;
  rubric: EvaluationRubric;
  estimatedSeconds: number;
}
```

### 检查策略

- 每章至少为核心目标取得一条有效证据；非核心目标可只做到接触或自我报告。
- 默认每 2～3 个任务最多一个 Checkpoint，根据目标密度调整。
- 单次预计 20～60 秒。
- 不直接重复正文句子。
- 优先考查边界、迁移和应用，而不是术语回忆。
- 开放式答案由模型按 Rubric 评估，结构化选择由程序确定结果。
- **上线顺序**：结构化类型（`scenario_choice`、`sequence`）先上线；开放式类型（`self_explanation`、`micro_practice`、`error_diagnosis`）依赖模型评估可信度，必须先在固定回归样本上验证评分与人工判定的一致性达标，未达标前不启用、不产生证据。

### 评估结果

```ts
interface CheckpointEvaluation {
  checkpointId: string;
  outcome: 'demonstrated' | 'partial' | 'not_demonstrated' | 'skipped';
  score?: number;
  confidence: number;
  misconceptionCodes: string[];
  feedback: string;
  nextAction: 'continue' | 'remediate_here' | 'insert_remediation_task';
}
```

### 补救流程

```text
未证明理解
  ↓
识别错误类型，而不是只判断对错
  ↓
选择不同于首次讲解的补救方式
  ↓
追加短补救内容
  ↓
用户重新尝试一个等价但不相同的检查
  ↓
记录补救前后证据
```

补救最多连续两轮。仍未证明理解时：

- 明确告诉用户本目标尚不稳定。
- 允许继续，但标记为待复习或建议补前置。
- 不伪造“掌握”。
- 避免把用户锁死在无限循环中。

## 2.8 章节完成

章节完成不是“所有内容已展示”，而是：

- 必需任务已完成或明确跳过。
- 所有核心目标都已接触。
- 要求 demonstration 的目标已有证据，或被明确标记为未验证。
- 没有仍在流式生成的请求。
- Chapter Runtime 已持久化。

### Chapter Recap

Recap 应短而有用：

```ts
interface ChapterRecap {
  chapterId: string;
  keyTakeaways: string[];
  demonstratedObjectives: string[];
  fragileObjectives: string[];
  unresolvedQuestions: string[];
  recommendedReview?: string;
  nextChapterPreview?: string;
}
```

Recap 不应重新生成一篇章节摘要；它要帮助用户识别“我带走了什么、哪里还不稳、下一步是什么”。

## 3. 状态机

## 3.1 章节状态机

```text
not_started
  → planning
  → learning
  ↔ awaiting_user
  ↔ checking
  ↔ remediating
  → completing
  → completed
```

异常状态不单独替代业务状态，而由当前请求记录：

```ts
interface PendingRequest {
  requestId: string;
  kind: 'chapter_plan' | 'task' | 'tutor' | 'checkpoint' | 'recap';
  status: 'pending' | 'streaming' | 'failed';
  attempt: number;
  startedAt: number;
  errorCode?: string;
}
```

### 合法转换规则

- `not_started → planning`：无有效 Chapter Plan。
- `planning → learning`：计划通过校验并持久化。
- `learning → awaiting_user`：当前任务内容完成。
- `learning → learning`（任务 `streaming → partial_paused`）：用户在流式生成中提问，当前块完成后暂停剩余块生成（见 §2.6.1）。
- `partial_paused → streaming`：回答完成且用户选择继续本节，同一任务新 attempt 恢复剩余块。
- `awaiting_user → learning`：用户继续，且下一任务可用或开始生成。
- `awaiting_user → checking`：当前任务需要 Checkpoint。
- `checking → remediating`：证据不足且需要补救。
- `checking/remediating → awaiting_user`：评估或补救完成。
- `awaiting_user → completing`：最后任务完成且章节条件满足。
- `completing → completed`：Recap 和状态写入成功。

所有转换通过领域函数完成，页面组件不能任意改字符串状态。

```ts
  teachingContext: TeachingContextPayload;
}
```

## 4.3 流内辅导

```http
POST /api/learning/v2/tutor/stream
```

请求包含当前任务上下文、相关 Stream 摘要和用户输入。响应先返回决策事件，再流式返回回答块。

## 4.4 评估 Checkpoint

```http
POST /api/learning/v2/checkpoints/evaluate
```

结构化题可以在服务端规则评估；开放式题调用 Python Agent。统一返回 `CheckpointEvaluation`。

## 4.5 完成章节

```http
POST /api/learning/v2/chapters/complete
```

必须在服务端或统一存储层再次校验完成条件，避免仅由客户端按钮将章节标为完成。

## 5. SSE 协议

所有事件使用统一外壳：

```ts
interface LearningSseEvent<T> {
  eventId: string;
  requestId: string;
  type: string;
  courseId: string;
  chapterId: string;
  taskId?: string;
  planVersion: number;
  sequence: number;
  timestamp: number;
  payload: T;
}
```

### 任务事件

```text
task_started
content_block_started
content_block_delta
content_block_completed
sources_ready
task_completed
```

### Tutor 事件

```text
tutor_decision
tutor_answer_started
content_block_started
content_block_delta
content_block_completed
tutor_answer_completed
```

### 通用事件

```text
request_warning
request_error
request_completed
```

规则：

- `sequence` 在单请求内严格递增。
- 客户端按 `eventId` 去重。
- `request_completed` 表示传输完成，不等于业务对象已持久化；持久化成功需有明确状态更新。
- 错误事件包含稳定 `code`、可展示 `message`、`retryable`，但不向用户暴露内部堆栈。
- 客户端使用行缓冲解析 SSE，处理跨 chunk 的 UTF-8 和多行事件。

## 6. 预取、缓存与并发

## 6.1 预取规则

> **Spike 实测依据（2026-08-31，`muses/deepseek-v4-flash`，via `/spike/waterfall`）**：单任务（300～500 字 markdown）流式生成首字约 0.3s，全部完成约 3.5～4.2s；任务衔接通过注入前序任务标题即可自然承接、不重复。结论：P1a 即时生成的边界等待可接受，预取延后到 P1b 成立；任务粒度按 300～500 字/1～3 分钟设计成立。

- 预取从 P1b 才开始；P1a 不做预取，靠任务短 + 流式输出掩盖等待（P4 之前计划版本不变，预取收益低而并发复杂度高）。
- 最多预取当前任务之后的一个任务。
- 在当前任务生成完成后开始预取下一任务。
- 预取绑定 `planId + planVersion + taskId`。
- 用户问题不会默认使预取失效；只有计划补丁改变该任务目标或顺序时才失效。
- 废弃预取可以保留短期诊断记录，但不能进入用户学习流。

## 6.1.1 本地存储治理（P1 落地）

- 每章学习流使用独立 localStorage key（如 `{课程key}:chapter:{chapterId}`），不并入课程主对象，避免单 key 读写放大和配额集中。
- 章节完成时压缩归档：保留 Recap、证据摘要和任务标题列表；正文块替换为摘要，原文不再保留在本地。
- 写入失败（配额超限）时提示用户并优先归档最旧的已完成章节，不静默丢数据。
- 现有存储前缀 `ai-learning-data-v2` 是历史命名，与 `protocolVersion: 2` 无关，不得混用判断逻辑。

## 6.2 幂等

以下操作必须提供幂等键：

- 创建 Chapter Plan。
- 生成 Task Attempt。
- 提交 Checkpoint。
- 完成章节。

同一幂等键的重复请求应返回既有结果或继续既有流，不能生成重复任务和重复证据。

## 6.3 并发冲突

典型冲突：

- 用户连续点击两次继续。
- 页面 A 和页面 B 同时推进同一课程。
- 预取尚未完成，用户提问导致计划版本变化。
- 刷新后旧请求仍返回事件。

处理原则：

- 前端交互期间禁用重复提交只是体验保护，不是最终保障。
- 写入层使用 `expectedVersion` 或等价的乐观锁。
- 旧版本结果拒绝写入当前运行时。
- 已完成操作返回当前结果，保证安全重试。

## 7. 错误处理与恢复

| 场景 | 用户体验 | 系统行为 |
|---|---|---|
| Chapter Plan 失败 | 显示明确错误与重试 | 保留课程目录，不创建半成品计划 |
| 当前任务中断 | 保留已完成块，当前块显示失败 | 从当前任务新 attempt 重试 |
| 预取失败 | 默认不打扰当前阅读 | 用户继续时即时生成并展示等待状态 |
| Tutor 失败 | 用户问题保留，回答位显示重试 | 不影响主任务继续 |
| Checkpoint 评估失败 | 保留用户答案，允许重试或稍后 | 不写入伪造证据 |
| 持久化失败 | 显示非阻断警告，但不可宣称已保存 | 重试写入并避免推进依赖状态 |
| 计划版本冲突 | 提示内容已更新并恢复最新状态 | 丢弃旧响应，重新读取状态 |

禁止使用与真实成功无法区分的静默降级内容。若必须使用本地兜底，应标明 `degraded: true`，且不能产生 mastery 证据。

## 8. Prompt 与模型职责

建议按职责拆分 Prompt：

```text
outline_v2
chapter_plan_v2
task_content_v2
tutor_decision_v2
tutor_answer_v2
checkpoint_generate_v2
checkpoint_evaluate_v2
chapter_recap_v2
```

### Prompt 通用输入

- 明确任务目标和输出 Schema。
- 只注入当前职责需要的上下文。
- 标明用户已确认事实与模型推断的区别。
- 标明禁止重复、禁止越界和长度预算。
- 注入 Prompt 版本，便于回归。

### Prompt 通用输出

- 结构化结果必须经过 Schema 校验。
- 正文使用内容块协议，不依赖前端从 Markdown 猜测业务类型。
- 不输出或保存隐藏思维过程。
- 决策输出 `reasonCode` 与置信度。
- 引用事实时返回来源元数据。

### 搜索策略

必须搜索或校验：

- 用户要求最新信息。
- 版本、政策、价格、产品能力等时效事实。
- 高风险领域的重要结论。
- 用户指定来源或上传资料。
- 模型对关键事实不确定。

通常无需搜索：

- 稳定基础知识。
- 基于已给材料的解释。
- 单纯换讲法或增加例子。

搜索结果先形成简短证据包，再注入内容生成，不直接将全量网页塞进 Prompt。

## 10. 测试策略

## 10.1 单元测试

- Blueprint 与 Chapter Plan 校验。
- 状态机合法/非法转换。
- Stream Reducer 的事件去重和顺序处理。
- `planVersion` 失效规则。
- 幂等请求处理。
- Checkpoint 规则评估。
- Evidence 聚合规则。

## 10.2 集成测试

- 从创建计划到完成 Task 1。
- SSE 被拆成任意 chunk 时仍正确解析中文和结构化事件。
- 流中断后重试不重复追加内容。
- 预取成功、失败、废弃三条路径。
- Tutor 回答进入 Stream 后可刷新恢复。
- Checkpoint → 补救 → 再验证完整闭环。
- 旧 V1 课程仍走旧渲染器。

## 10.3 Prompt 回归

建立固定样本：

- 初学者概念课。
- 有经验用户快速补齐。
- 实操技能课。
- 问题解决型课程。
- 用户明确要求跳过基础。
- 前置知识判断错误。
- 用户追问、质疑和目标偏移。

检查：

- Schema 通过率。
- 目标覆盖。
- 重复内容。
- 难度匹配。
- 答疑是否回到主线。
- Checkpoint 是否真正验证目标。

## 10.4 E2E

至少覆盖：

1. 新建 V2 课程并完成第一章。
2. 任务生成中刷新并恢复。
3. 提问后继续学习。
4. Checkpoint 答错、补救、重新作答。
5. 旧课程打开和完成无回归。
6. 移动端输入框、滚动和安全区域正确。

3. 支持插入、压缩、加深和重排未展示任务。

## 13. 明确禁止的实现捷径

- 用一个超大 Prompt 一次生成计划、正文、题目和 Recap。
- 让前端从 Markdown 标题猜测 Stream Item 类型。
- 仅在 React 本地状态保存学习流。
- 以点击继续或停留时间直接增加 mastery。
- 每次用户输入都让模型自由决定任意工具或改写计划。
- 重试时直接清空已展示内容。
- 预取结果不校验计划版本。
- 为了兼容而把 V1/V2 字段混在一个无版本对象里。
- 在没有测试和指标的情况下删除 V1 回退路径。
- 将归档文档中的旧 Action、阈值或字段视为当前需求。
