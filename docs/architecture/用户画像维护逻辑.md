# 用户画像维护逻辑

## 全局视角

用户画像不是一张静态表单，而是一个**随学习行为持续演化的动态模型**。它从两个源头吸收信号：

1. **显式信号**：用户主动填写的信息（目标岗位、工作经历、教育背景）
2. **隐式信号**：学习行为中自动提取的信号（答题对错、聊天偏好、困惑表达、节点完成）

两条信号流最终汇聚到 **V3 记忆模型**，通过三种 Payload（Planning/Teaching/Chat）在不同场景驱动个性化。

```
显式填写 → LLM 提取洞察 → stableFacts/goals
                                    ↓
答题/完成/聊天 → 事件聚合 → conceptProjections/topicProjections
                                    ↓
                          MemoryStoreV3（统一数据源）
                                    ↓
                    ┌───────────────┼───────────────┐
                    ↓               ↓               ↓
               Planning        Teaching         Chat
              （课程规划）    （内容教学）     （聊天辅导）
```

## 一、显式画像：从用户填写到结构化洞察

### 1.1 用户填写了什么

| 字段 | 业务含义 |
|------|---------|
| name | 姓名 |
| targetJob | 目标岗位 — 决定课程方向的核心锚点 |
| workExperience[] | 工作经历（公司/职位/描述） |
| education[] | 教育背景（学校/专业） |

### 1.2 LLM 提取的 7 个洞察维度

用户填写的原始文本经 LLM 处理，提取结构化洞察：

| 维度 | 条数限制 | 字数限制 | 提取规则 |
|------|---------|---------|---------|
| workSummary | 最多 5 条 | 15-30 字/条 | 提取具体产品/项目/职责，提炼领域和技能 |
| educationSummary | 最多 3 条 | 15-30 字/条 | 提取相关专业方向，与目标岗位关联 |
| analogyExperiences | 最多 3 条 | 20-40 字/条 | 具体做过的事，可用于类比教学的真实场景 |
| learningStyle | 1 个值 | — | 理论型/实践型 |
| technicalLevel | 1 个值 | — | 入门级/业务级/专家型 |
| valuePriorities | 最多 3 条 | 2-6 字/条 | 最看重的方向 |
| summary | 1 条 | 30-50 字 | 核心背景 + 目标方向 |

**严格约束**：只提取事实不推测、必须具体可操作、过滤空泛描述。

### 1.3 洞察如何流入记忆系统

`syncProfileToV3()` 将洞察转化为 V3 的 stableFacts：

| 洞察来源 | 转化为 | confidence |
|---------|--------|-----------|
| 用户姓名 | identity fact | 0.95 |
| 目标岗位 | goal fact | 0.95 |
| workSummary | knowledge_background fact | 0.82 |
| educationSummary | knowledge_background fact | 0.80 |
| analogyExperiences | analogy_experience fact | 0.80 |

confidence 差异反映来源可靠性：直接填写（0.95）> LLM 提取（0.80-0.82）。

## 二、隐式画像：从学习行为到概念掌握度

### 2.1 六类行为事件

| 事件 | 触发时机 | 更新什么 |
|------|---------|---------|
| question_answered | 每次答题 | conceptProjection 的 masteryScore / recentErrors / recentSuccesses |
| node_completed | 完成章节 | conceptProjection 升到至少 0.62 + episodicProjection |
| chat_user_message | 聊天中表达困惑 | conceptProjection 限制 ≤ 0.4 + 偏好检测 |
| course_generated | 课程生成完成 | episodicProjection（课程记录） |
| chat_session_summarized | 聊天结束 | episodicProjection（聊天记录） |
| 掌握信号 | 聊天中说"我懂了" | conceptProjection 记录 node_completed |

### 2.2 概念掌握度的计算规则

**核心数值**：

| 行为 | masteryScore 变化 | 设计意图 |
|------|------------------|---------|
| 答对 | +0.18 | 约 6 次答对从 0 升到 1.0 |
| 答错 | -0.22 | 约 5 次答错从 1.0 降到 0；**答错影响大于答对** |
| 节点完成 | 至少 0.62 | 完成教学 ≠ 掌握，只到 fragile 状态 |
| 表达困惑 | 限制 ≤ 0.4 | 困惑概念永远在 learning/unknown 状态 |

**为什么答错扣更多？** 虚假掌握（自以为会了）比低估掌握度的危害更大——前者导致跳过关键内容。

### 2.3 概念状态四档判定

| 状态 | 条件 | 业务含义 |
|------|------|---------|
| **mastered** | masteryScore ≥ 0.78 且近期无错误 | 稳定掌握，可跳过 |
| **fragile** | masteryScore ≥ 0.6 | 表面掌握但不稳固，需巩固 |
| **learning** | masteryScore > 0 或有近期错误 | 正在学习中 |
| **unknown** | masteryScore = 0 且无错误 | 从未接触 |

**mastered 为什么是 0.78 而非 1.0？** 不需要完美分数，接近 80% 且无近期错误即可视为掌握——降低门槛让系统能更快识别可跳过的内容。

**为什么还要"无近期错误"？** 分数高但近期有错误意味着"曾经会但现在忘了"，不应算掌握。

### 2.4 主题熟悉度的计算

主题熟悉度 = 该主题下所有概念的 masteryScore 平均值（上限 0.95）。

| 水平 | familiarityScore | 含义 |
|------|-----------------|------|
| advanced | ≥ 0.82 | 大部分概念已掌握 |
| intermediate | 0.62 - 0.81 | 中等熟悉 |
| beginner | 0.38 - 0.61 | 初步接触 |
| novice | < 0.38 | 几乎零基础 |

阈值非等距（0.38/0.62/0.82 间距递减），体现"越高级越难达到"的学习规律。

## 三、遗忘曲线：知识的自然衰减

### 3.1 衰减公式

```
衰减后掌握度 = masteryScore × e^(-天数/30)
```

30 天半衰期：30 天不复习掌握度减半，60 天降至 25%，90 天降至 12.5%。

### 3.2 为什么选 30 天而非更激进的艾宾浩斯曲线？

艾宾浩斯原始数据显示 1 个月后仅保留约 21%。如果严格遵循，用户几天不学就"全忘了"，对学习体验极不友好。30 天半衰期意味着**每周有学习行为就不会严重衰减**，更符合间隔重复的实际应用（Anki 等系统默认也在 21-30 天范围）。

### 3.3 新鲜度衰减（21 天半衰期）

```
freshnessScore = e^(-天数/21)
```

新鲜度衰减比掌握度更快——一个月前的学习行为对"你最近在关注什么"的参考价值下降更快。这在概念检索排序中占 20% 权重。

### 3.4 复习间隔

| 答题结果 | 下次复习时间 |
|---------|------------|
| 答对 | 7 天后 |
| 答错 | 2 天后 |

### 3.5 概念清理

衰减后掌握度 < 0.3 且超过 90 天未更新的概念会被删除。0.3 远低于 learning 阈值（0.6），90 天约 3 个月——一个概念如果 3 个月内衰减到 0.3 以下，视为"已遗忘且不再相关"。

## 四、偏好系统：从聊天中学习用户习惯

### 4.1 偏好检测规则

| 用户说的关键词 | 识别为 | confidence |
|--------------|--------|-----------|
| "一步一步""分步骤""逐步" | 分步拆解 | 0.74 |
| "举个例子""例如""比如" | 例子驱动 | 0.72 |
| "类比""打比方" | 类比解释 | 0.72 |
| "简单点""通俗点""白话" | 通俗解释 | 0.68 |
| "区别""对比" | 对比讲解 | 0.70 |

**confidence 差异**："分步拆解"最高（0.74），因为"一步一步"几乎只在请求分步讲解时出现；"通俗解释"最低（0.68），因为"简单点"可能只是抱怨难度而非真正偏好。

### 4.2 偏好的置信度累积

- 首次检测：confidence = 0.72
- 再次匹配：+0.05（上限 0.95）
- 约需 5-6 次重复才能达到高置信度
- **偏好置信度只升不降**——这是当前设计的风险点（早期误检无法消除）

### 4.3 偏好如何影响课程生成

偏好写入 V3 的 `profile.preferences`，通过 Teaching/Chat Payload 中的 `preferredExplanationStyles` 传入 prompt，影响 LLM 生成风格。

## 五、困惑信号检测：识别知识缺口

### 5.1 检测规则

匹配 13 个关键词（"没懂""不懂""还是不明白""有点懵""看不懂""卡住了"等）。

### 5.2 置信度设计

```
confidence = min(0.9, 0.55 + 重复困惑次数 × 0.07)
```

- 单次困惑：0.62（刚过半，不足以确认）
- 两次困惑：0.69
- 多次困惑：逐步升高，上限 0.9

### 5.3 对掌握度的影响

表达困惑的概念 masteryScore 被限制 ≤ 0.4，确保该概念始终处于 learning/unknown 状态，不会被误判为已掌握。

## 六、记忆精炼：LLM 驱动的深度分析

### 6.1 触发条件

- 至少 3 条用户消息（1-2 条不足以构成趋势）
- 距上次精炼 ≥ 5 分钟（避免过度调用）

### 6.2 精炼产出

| 产出 | 业务含义 |
|------|---------|
| learningSummary | 学习旅程总结（旅程/当前焦点/学习者洞察/需关注领域） |
| preferenceUpdates | 偏好更新（kind/value/evidence/confidence） |
| conceptCorrections | 概念掌握度修正（只修正差异 > 0.15 的） |

### 6.3 为什么概念修正门槛是 0.15？

0.15 约等于一次答题的增量（0.18），只有 LLM 认为差异大到"相当于一次完整答题的影响"时才修正。防止 LLM 的微小幻觉频繁覆盖行为数据。

### 6.4 偏好更新策略

`confidence = max(现有, 新值)`——只升不降。防止 LLM 精炼降低行为数据积累的置信度，但也造成了早期误检偏好无法消除的风险。

## 七、推荐系统

### 7.1 推荐策略

5 个输入维度：
1. targetJob → 保证相关性
2. insights（背景洞察）→ 个性化
3. existingTopics（已学课程）→ 避免重复、发现缺口
4. recentTopics（最近关注）→ 延续当前兴趣
5. previousRecommendations → 避免重复推荐

### 7.2 约束

- 每个主题控制在 2-3 个核心知识点
- 具体务实，不推荐泛泛入门内容

### 7.3 已知问题

**"换一批"按钮实际无效**：代码中有早期退出逻辑 `if (recommendations.length > 0) return`，阻止了二次生成。用户看到推荐后点"换一批"不会触发新请求。

**去重依赖 LLM 语义理解**：没有代码层硬去重，LLM 可能输出语义相似但表述不同的主题。

## 八、数据规模限制

| 数据类型 | 上限 | 淘汰策略 | 设计考量 |
|---------|------|---------|---------|
| 概念 | 200 | 按 `衰减掌握度×0.7 + 新鲜度×0.3` 排序 | 覆盖 3-5 个领域，一个岗位学习者够用 |
| 主题 | 50 | 按更新时间 | 每 Topic 约 4 概念，学习广度上限 |
| 课程 | 30 | 按更新时间 | 约 2-3 个月持续学习量 |
| 事件（热数据） | 180 | — | 约 2-3 周活跃行为量 |
| 事件（重要） | 40 | — | 课程生成和聊天摘要等关键事件 |
| 偏好 | 12 | — | 防止偏好膨胀 |

概念淘汰评分：70% 权重给知识保留状态，30% 给时效性。"既掌握得好又最近活跃"优先保留。

## 九、概念依赖图谱

- 从 CourseBlueprint 的 `globalConcepts` 和 `prerequisiteConceptIds` 构建
- 递归查询最多 2 层前置依赖（超过 2 层说明底层知识缺口太深，应建议先学更基础的课程）
- 别名匹配解决"同一概念在不同课程叫不同名字"的问题（如"工具调用" vs "tool call"）
- 当前别名表仅 4 组，规模较小，大部分匹配仍依赖字符串相似度

## 十、关键设计思想与风险点

### 设计思想

| 设计 | 策略 | 意图 |
|------|------|------|
| 答错权重 > 答对 | -0.22 vs +0.18 | 宁可低估掌握度，不让用户跳过关键内容 |
| 节点完成 ≠ 掌握 | 完成只升到 0.62 | 需要答题验证才算掌握 |
| mastered 双条件 | ≥ 0.78 且无近期错误 | 防止"曾经会但现在忘了" |
| 多次信号才确认 | 偏好需 5-6 次才到高置信度 | 防止偶然措辞被永久记录 |
| 概念修正高门槛 | 差异 > 0.15 才修正 | 防止 LLM 幻觉覆盖行为数据 |
| 显式 > 隐式 | 直接填写 0.95, LLM 提取 0.80 | 来源越可靠置信度越高 |

### 风险点

| 风险 | 说明 |
|------|------|
| 阈值均为经验值 | 0.78/0.6/0.38/0.62/0.18/0.22/30天等无 A/B 测试支撑，不可配置 |
| 偏好只升不降 | 早期误检的偏好永远无法消除 |
| 概念修正门槛可能过高 | 0.15 差异内的小但重要修正会被忽略 |
| 遗忘曲线与复习间隔不一致 | 30 天半衰期但答对后 7 天复习，可能复习过频 |
| 别名表规模极小 | 仅 4 组，概念匹配大部分依赖字符串相似度 |
| "换一批"推荐按钮无效 | 代码逻辑阻止了二次生成 |
| 去重依赖 LLM 语义理解 | 无代码层硬去重，可能输出语义重复推荐 |
