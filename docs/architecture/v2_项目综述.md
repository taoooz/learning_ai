## 2. 产品判断

### 2.1 当前问题

现有产品已经具备课程蓝图、章节目录、知识卡片、练习题、聊天助手和用户记忆，但学习体验仍以“内容资产”为中心：

```text
先生成章节内容
→ 用户逐张查看卡片
→ 集中完成练习题
→ 进入下一章
```

主要问题：

- 用户进入章节后，要等待一批内容完成生成，首个有效内容出现较慢。
- 每次只展示一张卡片，已经学过的上下文从视野中消失，不像自然阅读与思考。
- 聊天在独立浮层中发生，问题和回答没有成为课程学习轨迹的一部分。
- 练习集中在末尾，反馈来得太晚；但单纯点击“继续”又不足以证明理解。
- 课程生成、答疑和掌握度更新彼此相邻，却没有形成统一的教学决策闭环。
- AI 容易一次生成过多内容，无法充分利用用户刚刚暴露的疑问调整后续教学。

### 2.2 V2 核心价值

V2 不只是把卡片改成长页面，而是把产品从“AI 课程内容生成器”升级为“持续做下一步教学决策的 AI Tutor”。

```text
稳定的课程路线
→ 小步生成和呈现
→ 用户阅读、提问或接受检查
→ 收集学习证据
→ 决定继续、补救、换讲法或提速
→ 保持主线稳定地完成目标
```

对用户的价值：

- **更快开始**：进入章节后立即看到第一段有意义内容。
- **更好理解**：内容按认知目标拆成短任务，避免一次灌输整章。
- **随处可问**：问题在当前内容下方得到回答，不离开学习上下文。
- **卡住即修复**：系统在困惑发生处补例子、换讲法或补前置知识。
- **不被频繁考试**：低压力学习为主，只在关键目标处进行短验证。
- **持续个性化**：系统逐渐知道用户会什么、哪里不稳、哪种补救有效。

对业务的价值：

- 提高首屏进入率、任务继续率、章节完成率和跨日返回率。
- 从“生成了多少内容”转向“完成了多少可验证学习目标”。
- 形成难以复制的学习数据闭环：目标、内容、问题、证据、补救效果彼此关联。
- 将课程质量从主观 Prompt 调优升级为可观测、可回归、可迭代的系统能力。

## 3. 产品定位

### 3.1 一句话定位

**用户输入任何学习目标，AI 为其规划稳定路线，并在连续学习过程中根据理解证据实时调整讲法和下一步。**

### 3.2 核心差异

V2 的核心不是“任何主题都能生成”，而是：

> **课程路线稳定，章节内部自适应；用户始终掌握推进权，AI 负责判断下一步最值得教什么。**

### 3.3 非目标

V2 当前不追求：

- 完全自由、不可预测的自主 Agent。
- 每条行为都触发一次 LLM。
- 无限向下生成的内容信息流。
- 用阅读时长或点击继续推断“已经掌握”。
- 每个任务都强制答题。
- 一开始就重构所有课程、记忆和存储系统。
- 复制竞品的视觉界面或未经证实的内部架构。

## 4. 设计原则

### 4.1 路线稳定，局部适应

- Course Blueprint 和章节目录是用户的方向感来源，不应因单次问题频繁变化。
- 动态调整优先发生在当前解释和本章剩余任务内。
- 只有用户明确改变目标，或发现严重前置缺口时，才考虑修改更高层路线。

### 4.2 小步交付，任务边界停顿

- 每个任务服务一个主要学习目标。
- 单个任务建议 1～3 分钟完成。
- 当前任务完成后暂停，等待用户继续、提问或反馈。
- 后续任务可以预取一个，但不能无界提前生成。

### 4.3 学习流连续，用户问题入流

- 已学内容保留在上方，新内容向下追加。
- 用户问题、AI 回答、补充案例和检查结果都是学习流的一部分。
- 学习页不是聊天页；提问服务于当前课程目标，回答后应自然回到主线。

### 4.4 证据优先，不把行为当掌握

- 点击继续、阅读时长、页面停留只能反映参与度，不能证明理解。
- 自我报告是弱证据。
- 场景判断、自我解释、微实践和后续迁移表现才是掌握度的主要依据。
- 答错不是失败，而是决定补救方式的教学输入。

### 4.5 规则控制流程，模型处理语义

程序负责：

- 状态机、版本、持久化、缓存、重试、推进、幂等和权限。

模型负责：

- 需求理解、任务规划、内容生成、开放问题评估、问题分类和教学方式选择。

不应让模型直接控制不可逆状态，也不应为确定性操作调用模型。

### 4.6 先验证核心体验，再扩大智能程度

实施顺序必须是：

```text
协议和兼容
→ 累积式学习流
→ 流内答疑
→ 证据型检查与补救
→ 有边界的动态调度
→ 服务端持久化与质量规模化
```

不能跳过基础状态模型，直接实现完整 Director Agent。

## 5. 目标用户旅程

```text
用户输入学习主题
  ↓
Outline 判断目标、起点和边界；必要时最多澄清 3 次
  ↓
生成 Course Blueprint 和目标导向的章节目录
  ↓
预热第一章 Chapter Plan
  ↓
用户进入章节
  ↓
恢复已有进度，或流式生成 Task 1
  ↓
┌──────────────── 章节学习循环 ────────────────┐
│ 任务内容向下追加                              │
│   ↓                                          │
│ 到达任务边界，系统暂停                        │
│   ├─ 用户点击继续 → 展示/生成下一任务          │
│   ├─ 用户提问 → 原地流式回答                   │
│   ├─ 用户要求例子/换讲法 → 原地追加补充        │
│   └─ 到达关键目标 → 20～60 秒轻量理解检查      │
│                         ↓                     │
│              继续 / 补救 / 换讲法 / 提速       │
└──────────────────────────────────────────────┘
  ↓
章节目标完成
  ↓
轻量 Recap + 学习证据聚合 + 下一章预告
  ↓
进入下一章或稍后继续
```

### 5.1 用户始终可做的事

- 返回查看本章已经出现的内容。
- 针对当前内容直接提问。
- 请求一个例子、换种讲法或更深入。
- 点击继续推进。
- 退出并在之后恢复。

### 5.2 系统不会做的事

- 因为用户停留时间长就自动追加大量内容。
- 因为一次提问就重写整门课程。
- 把点击继续记录成“已掌握”。
- 在后台生成结果失效后仍展示旧版本内容。
- 生成失败时清空已经学过的内容。

## 6. 核心业务对象

V2 采用四层业务对象：

```text
Course Blueprint
  └─ Chapter
      └─ Chapter Plan
          └─ Learning Stream
```

### 6.1 Course Blueprint

定义整门课的稳定契约：

- 用户学习意图和目标场景。
- 用户起点和明确边界。
- 可验证的课程目标。
- 必须覆盖、可跳过和高风险概念。
- 章节顺序和依赖。
- 课程完成标准。

### 6.2 Chapter

章节是一组相关学习目标，不只是内容容器。每章应回答：

1. 本章解决哪个认知或能力缺口？
2. 学完后用户能做出什么判断、解释或操作？
3. 哪些概念必须形成理解证据？
4. 哪些内容可以按用户状态压缩？

### 6.3 Chapter Plan

将章节目标拆为 3～7 个短任务。计划保存任务元数据，不要求一次生成所有正文。

### 6.4 Learning Stream

学习流保存用户实际经历过的内容和交互：

- 教学内容块；
- 用户问题；
- AI 回答；
- 补救内容；
- 理解检查；
- 任务过渡；
- 章节回顾。

它是用户学习过程的事实记录，已展示内容不可被后台静默改写。

## 7. 能力分层

### 7.1 课程规划能力

- 识别学习意图：概念理解、技能掌握、问题解决、快速复习。
- 明确用户已知、未知、排除项和目标场景。
- 将章节目标写成可观察行为，而非“深入理解”等空泛描述。
- 将目标拆成认知负荷可控的任务序列。

### 7.2 内容教学能力

- 根据任务目标选择解释、案例、对比、步骤、推导、反例等方式。
- 控制术语密度、信息密度和内容长度。
- 承接上一个任务，避免重复背景。
- 只在真正有帮助时生成图表或代码。

### 7.3 流内辅导能力

- 回答当前内容的小问题。
- 在原地补一个例子、反例或不同解释。
- 识别前置知识缺口。
- 区分局部疑问、教学偏好、目标变化和继续意图。

### 7.4 理解验证能力

- 将检查绑定到具体目标和概念。
- 优先使用场景判断、自我解释和微实践。
- 根据证据决定继续、补救或提速。
- 补救后重新验证，而不是只展示正确答案。

### 7.5 学习记忆能力

- 区分稳定画像、章节运行时状态和当前任务上下文。
- 区分参与行为、困惑信号和掌握证据。
- 记录哪种补救方式对该用户有效。
- 让后续课程减少重复并更快进入合适深度。

## 8. 系统边界与职责

### 8.1 前端

负责：

- 渲染累积式学习流。
- 消费结构化 SSE 事件。
- 管理当前交互状态和滚动位置。
- 提供继续、提问、反馈和检查交互。
- 本地乐观更新与失败恢复。
- 在迁移期兼容 V1 课程。

不负责：

- 自行推断教学动作。
- 根据展示文本解析核心业务状态。
- 直接修改长期掌握度。

### 8.2 Next.js API 层

负责：

- 鉴权和请求校验。
- 将前端协议转换为 Python Agent 请求。
- 统一错误格式和流式透传。
- Feature Flag 与 V1/V2 路由选择。
- 未来服务端存储接入。

### 8.3 Python Agent

负责：

- 构建课程、章节计划和任务内容 Prompt。
- 必要时使用搜索工具。
- 输出结构化事件或结构化 JSON。
- 处理流内问题的语义分类和回答。
- 评估开放式理解证据。

不负责：

- 成为唯一状态源。
- 直接决定数据库写入成功与否。
- 在没有版本校验时覆盖计划。

### 8.4 状态与记忆层

负责：

- 保存 Course Blueprint、Chapter Plan、Learning Stream 和 Cursor。
- 维护计划版本与幂等键。
- 保存学习证据和画像投影。
- 支持退出恢复与跨阶段兼容。

## 9. 分阶段实施路线

阶段是硬边界。每个阶段应独立可发布、可验证、可回退。

### P0：协议、兼容和观测基础

**目标**：建立 V2 的稳定数据边界，不改变默认用户体验。

**类型定义范围原则：P0 只定义 P1 实际消费的类型。** Evidence、Checkpoint、补救等 P3 才使用的结构在 P3 开工前定稿，避免提前锁定后在 P1/P2 实现中返工。

范围：

- 新增 `protocolVersion: 2`。
- 定义 P1 所需核心类型：Chapter Plan、基础 Learning Stream Item（任务内容、任务过渡、系统通知）、Chapter Runtime State、SSE 事件外壳。
- 定义结构化 SSE 事件协议。
- 增加 V1/V2 Feature Flag。
- 旧课程继续走 V1；新试验课程可选择 V2。
- 建立生成阶段、耗时、错误和版本日志。

不做：

- 不重做学习页。
- 不实现流内答疑。
- 不更新用户掌握度规则。
- 不提前定义 Evidence/Checkpoint 详细类型（P3 前定稿即可）。

验收：

- 类型检查和协议测试通过。
- V1 行为无回归。
- V2 空壳数据可创建、序列化、恢复。
- 同一幂等键不会创建重复计划或任务。

### P1：累积式瀑布学习流 MVP

**目标**：验证“边生成、边学习、内容持续保留”的核心体验。

P1 是体验验证的关键路径，拆为两个可独立发布的切片，先跑通主循环，再补齐体验增强。

#### P1a：核心学习循环（必须最先跑通）

范围：

- 章节进入时读取或生成 Chapter Plan。
- Task 1 内容流式追加。
- 任务结束后显示“继续学习”。
- 点击后生成并流式展示下一任务（本切片不做预取，靠任务短 + 流式输出掩盖等待）。
- 已生成内容、当前任务和滚动锚点可恢复。
- 学习流按章节独立存储 key，控制单 key 体积（见 P1 存储治理）。
- 最后任务完成后显示简单完成态和下一章入口。

#### P1b：体验增强

范围：

- 最多预取当前任务之后的一个任务，绑定 `planId + planVersion + taskId`。
- 当前任务失败可单独重试，既有内容不丢失。
- 轻量 Recap 替代简单完成态。

> 预取放在 P1b 而非 P1a 的原因：预取 + 版本失效是并发复杂度的主要来源，而 P4 之前计划版本不会变化，P1a 阶段预取收益接近零。先验证主循环手感，再加预取。

#### P1 存储治理（不推迟到 P5）

Learning Stream 持久追加问答、补救、检查记录，单章体积几十 KB 起步，localStorage 5MB 配额可能在 P2～P3 见顶。P1 必须落地：

- 每章学习流使用独立存储 key，不并入课程主对象。
- 章节完成后压缩归档：保留 Recap 和证据摘要，正文块摘要化。
- 注意：现有存储前缀 `ai-learning-data-v2` 是历史命名，与本方案的 `protocolVersion: 2` 无关，实施时不得混淆。

不做：

- 不实现计划动态重排。
- 不依据学习行为更新掌握度。
- 不加入强制 Checkpoint。
- 不删除 V1 Cards/Questions 路径。

关键指标：

- 首个有效内容出现时间。
- Task 1 → Task 2 继续率。
- 章节完成率。
- 任务生成失败率。
- 预取命中率（P1b 起）。

### P2：流内提问与局部教学响应

**目标**：让答疑成为学习过程的一部分，而不是独立聊天功能。

范围：

- 学习页底部常驻输入框（流式生成中的提问行为见课程生成逻辑 §2.6.1）。
- 问题和回答作为 Stream Item 保存。
- 支持 `answer_inline`、`expand_current`、`switch_explanation`、`proceed`。
- 回答绑定课程、章节、任务和当前内容摘要。
- 回答结束后恢复“继续学习”。
- 保存困惑、偏好和问题主题，但暂不自动重排章节。
- V1 ChatWidget 与 V2 流内答疑并存期间，聊天提交、SSE 解析等底层逻辑（如 `useChatSubmit`）抽取共享，不复制两份。

不做：

- 不开放任意 `revise_plan`。
- 不因停留时间自动调用模型。
- 不因单次偏好表达立即修改长期画像。

关键指标：

- 提问率。
- 回答后继续率。
- 同一问题重复追问率。
- 用户主动要求换讲法的比例。
- 答疑请求失败率和首字延迟。

### P3：证据型理解检查与补救

**目标**：建立教学闭环，而不是只优化阅读体验。

范围：

- 关键目标处插入短 Checkpoint，不要求每任务都有。
- **结构化优先上线**：先启用程序可判分的场景选择和排序题；自我解释、微实践等开放式评估依赖模型按 Rubric 评分，须先通过 Prompt 回归样本验证达标后才启用（评估可信度是证据体系的根基，不能未经验证就投产）。
- 区分行为信号、自我报告和能力证据。
- 支持 `continue`、`remediate_here`、`insert_remediation_task`。
- 补救后使用不同但等价的检查重新验证。
- 学习证据写入章节状态，并在章节完成时聚合到长期画像。

关键指标：

- 首次检查通过率。
- 补救后通过率。
- 同概念后续再次困惑率。
- 检查导致退出率。
- 目标证据覆盖率。

### P4：有边界的动态教学调度

**目标**：基于可靠信号调整本章剩余路径。

范围：

- 支持压缩、提速、插入前置、调整深度和重排剩余任务。
- 所有调整基于 `planVersion` 和结构化操作。
- 每章动态调整次数有上限。
- 用户可看到简短、非技术化的调整提示。
- 高影响调整需高置信度或用户明确意图。
- 已展示内容不可删除或改写。

关键指标：

- 调整接受率。
- 调整后继续率。
- 被撤回或再次修改的比例。
- 每章插入任务数。
- 动态调整后的证据改善。

### P5：服务端持久化、质量系统与规模化

**目标**：将验证有效的 V2 变成可靠、可运营的正式系统。

范围：

- 服务端用户级课程和学习流存储。
- 多设备恢复。
- Prompt、模型、来源和计划版本追踪。
- 高风险内容事实校验。
- 质量样本集和离线回归。
- A/B 实验与用户反馈闭环。
- 成本、延迟、缓存和数据生命周期治理。

## 10. 成功指标

### 10.1 北极星指标

**每周完成且获得至少一条有效理解证据的学习目标数。**

它同时约束学习推进和真实理解，不能被长内容或高点击量虚增。

该指标依赖 P3 的证据体系，P3 之前不可测。P1/P2 期间使用代理指标：首个有效内容出现时间（TTFC）+ Task 1 → Task 2 继续率 + 章节完成率。

### 10.2 体验指标

- 首个有效内容出现时间（TTFC）。
- 任务继续率和章节完成率。
- 中途退出位置和跨日恢复率。
- 用户等待时间占学习时间的比例。
- 当前任务重试率。

### 10.3 教学指标

- 目标证据覆盖率。
- Checkpoint 首次通过率。
- 补救后通过率。
- 后续迁移任务表现。
- 已判定掌握概念的再次困惑率。

### 10.4 AI 与工程指标

- Chapter Plan 校验失败率。
- 内容重复率和用户报告错误率。
- SSE 中断率和恢复成功率。
- 预取命中率与废弃率。
- 单章节模型成本。
- 动态动作的接受率和回滚率。

## 11. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 瀑布流变成长文章 | 强制任务边界、单目标、长度预算和停顿 |
| 首屏仍然慢 | Plan 预热、Task 1 独立流式生成、结构化首块事件 |
| 问答喧宾夺主 | 回答绑定当前目标，结束后明确回到主线 |
| AI 频繁改计划 | 规则优先、阶段延后开放、次数与置信度限制 |
| 点击继续被误认为掌握 | 行为信号和能力证据分离 |
| 检查过多导致压力 | 只在关键目标处检查，控制在 20～60 秒 |
| 预取内容与新计划冲突 | `planVersion` 校验，旧结果废弃而非展示 |
| 本地数据持续膨胀 | P1 起每章独立 key + 完成后压缩归档；P5 服务端迁移 |
| 旧课程无法打开 | 协议版本化，V1 渲染路径保留至迁移完成 |
| 模型输出不稳定 | Schema 校验、局部修复、幂等重试、离线样本回归 |

## 12. 开发协作约束

其他 AI 或开发者实施时必须遵守：

1. **先读三份 V2 文档**，不得从归档文档推导当前需求。
2. **一次只实施一个阶段内的明确切片**，不得顺手加入后续阶段能力。
3. **保持 V1 兼容**，除非任务明确要求结束迁移。
4. **先定义或更新类型和契约，再写页面与 Prompt。**
5. **每个写操作必须幂等**，每个异步结果必须校验版本。
6. **已展示的学习流是事实记录，不能静默重写。**
7. **模型不直接写长期画像**，只输出候选信号或评估结果，由规则层聚合。
8. **点击、停留等参与行为不计入掌握度。**
9. **失败必须局部可恢复**，不能因单任务失败破坏整个章节。
10. **每个功能附测试、埋点和 CHANGELOG 更新。**
