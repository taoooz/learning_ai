# 课程生成与用户画像策略 V2

## 1. 核心判断

现有系统已经具备“记忆驱动的渐进个性化”基础，但课程体验仍偏向一次性内容生成：

```text
课程目录确定 → 每个章节生成多张卡片 → 生成练习题 → 完成章节
```

V2 的重点不是让 AI 一次生成更长、更完整的章节，而是把课程变成一个持续决策系统：

```text
课程目录确定 → 每章定义目标簇 → 初始化任务计划 → 每次只生成当前任务
  → 用户消费 → 理解检查 → 更新画像 → 决定下一步
```

第一阶段先收敛为“流式任务课程内容”：把单节点内的知识卡片 + 问题卡片，改成多个连续学习任务。每个任务完成一次讲解后暂停，由用户主动点击“继续”进入下一任务，暂时不生成练习题，也不做新的用户画像更新。

核心原则：

- 课程不是静态内容集合，而是围绕目标推进的学习路径。
- 章节不是内容容器，而是一个学习目标簇。
- 任务是最小学习推进单元，每个任务都必须有清晰目标和结束停顿。
- 个性化不只改变表达风格，更要改变下一步学什么、讲多深、是否补救。
- 用户画像的价值不是“记录用户”，而是减少下一次教学决策的不确定性。

## 2. 目标课程体验

### 2.1 用户看到的课程

课程页仍然保留清晰目录，让用户知道整体路径。但目录中的每一章应表达“学完能做什么”，而不是只表达“包含什么内容”。

示例：

```text
第 1 章：判断什么时候需要 RAG
目标：
1. 解释 RAG 和普通 Prompt 的区别
2. 判断一个业务场景是否需要外部知识库
3. 说清楚检索、召回、上下文注入各自的作用
完成标准：
能在 3 个业务场景中正确判断是否适合使用 RAG
```

### 2.2 用户进入章节后的体验

章节内部不再一次展示所有卡片，而是按任务推进：

```text
任务 1：从一个业务问题理解 RAG 为什么存在
  → 1-2 个短内容块
  → 用户点击继续

任务 2：拆解 RAG 的核心流程
  → 1-3 个短内容块
  → 用户点击继续

任务 3：对比 RAG、Fine-tuning、长上下文
  → 对比内容
  → 最后 1-2 句收束本节并引导下一节
```

每个任务结束都要停顿。第一阶段用户只通过“继续”推进；后续再加入针对当前任务内容的发问入口。这个停顿是体验和后续画像的关键：它让用户有节奏地消费内容，也为未来收集更细的学习信号留出位置。

### 2.3 好体验标准

| 标准 | 说明 |
|------|------|
| 短步推进 | 单次学习任务控制在 1-3 分钟，避免一次性灌入整章内容 |
| 每步有目标 | 用户知道当前任务解决什么问题 |
| 每步有停顿 | 讲解结束后暂停，让用户主动触发下一步 |
| 交互先极简 | 第一阶段只保留继续，避免过早引入复杂分支 |
| 发问后置 | 用户针对任务内容提问、影响后续任务排布，作为后续高级能力 |
| 目录稳定 | 动态调整主要发生在章节内部，不轻易推翻整门课 |

## 3. 第一阶段课程生成优化方案

### 3.1 阶段目标

第一阶段只优化课程生成和节点学习体验，用户画像升级后置。

当前节点内容：

```text
intro → card1 → card2 → ... → question1 → question2 → complete
```

第一阶段目标节点内容：

```text
intro
  → task1_streaming_content → 用户主动继续
  → task2_streaming_content → 用户主动继续
  → task3_streaming_content → 用户主动继续
  → final_task_with_next_node_bridge → complete
```

关键变化：

- 取消单独的知识卡片和问题卡片。
- 不生成练习题，不做答题正确率统计。
- 每个节点变成一组连续任务。
- 每个任务是一段有明确目标的流式讲解。
- 一个任务讲完后停住，等待用户主动触发下一步。
- 第一版任务间只有“继续”按钮。
- 如果当前任务是本节点最后一个任务，内容末尾补 1-2 句，提示本节收束并自然引导到下一节。
- 用户针对任务内容主动发问、发问后影响后续任务排布，作为后续高级能力处理。

### 3.2 已确认决策

| 决策点 | 第一阶段结论 |
|--------|--------------|
| 内容生成方式 | 逐任务流式生成。进入节点后生成任务计划和当前任务，生成过程直接展示给用户 |
| 任务间操作 | 只保留“继续” |
| 用户疑问 | 第一阶段不做。后续通过消息入口让用户针对任务内容发问，并可能影响后续任务排布 |
| 再讲/深入 | 第一阶段不做，作为用户发问能力的延伸 |
| 节点总结 | 不做单独总结页。最后一个任务末尾只提示用户进入下一节 |
| 练习题 | 彻底隐藏，不生成题卡。未来即使恢复练习，也作为任务内容类型之一 |
| 任务数量 | 每个节点 3-6 个任务 |
| NodeTaskPlan | 只包含任务骨架：`taskId`、`taskTitle`、`taskDescription` |
| 第一个任务内容 | 与 `NodeTaskPlan` 分开请求，因为任务内容要流式展示 |
| 任务计划预热 | 课程目录生成后预热第一个节点计划；上一个节点第一个任务内容生成完后，预热下一个节点计划 |

### 3.3 参考 Hyperlearn 的课程质量原则

Hyperlearn 值得借鉴的不是表层 UI，而是课程生成前的教学架构控制：

| 原则 | 对第一阶段的启发 |
|------|------------------|
| 需求解构 | 先识别学习意图、深度、已知项、排除项，再生成节点内容 |
| 单元聚类 | 把强相关概念聚成任务，避免一个任务塞入多个认知目标 |
| 认知负荷控制 | 每个任务控制信息密度，复杂概念拆成多步 |
| 任务动词化 | 任务标题用“理解、判断、对比、拆解、应用”等动词开头 |
| 梯度排序 | 从知识锚点到新概念，从直觉到机制，从机制到应用 |
| 约束对齐 | 不讲用户要求跳过的内容，不重复已掌握基础 |
| 内容模板匹配 | 根据任务动词选择解释、案例、对比、步骤、推导等内容形态 |
| 讲解后停顿 | 一个任务讲完必须暂停，让用户消费后再进入下一步 |

第一阶段不照搬 Hyperlearn 的题目和动态评分机制，先聚焦“课程内容质量”和“任务式讲解节奏”。

### 3.4 节点任务结构

每个课程节点生成一个 `NodeTaskPlan`。

```ts
type NodeTaskPlan = {
  nodeId: string
  nodeTitle: string
  nodeGoal: string
  tasks: NodeTask[]
}

type NodeTask = {
  taskId: string
  taskTitle: string
  taskDescription: string
}
```

任务数量建议：

| 节点复杂度 | 任务数 | 说明 |
|------------|--------|------|
| 简单节点 | 3 个 | 一个概念或一个技能点 |
| 中等节点 | 4-5 个 | 需要从概念到应用 |
| 复杂节点 | 5-6 个 | 包含多个依赖概念或强推理链路 |

任务标题示例：

- 建立直觉：为什么普通 Prompt 不够用
- 拆解机制：RAG 如何把外部知识塞进上下文
- 对比边界：RAG、Fine-tuning 和长上下文分别适合什么
- 识别误区：RAG 不是“让模型记住新知识”
- 连接应用：如何判断一个业务问题是否该用 RAG

### 3.5 流式内容块

任务内容不放在 `NodeTaskPlan` 中，而是在用户进入某个任务时单独请求并流式展示。每个任务内容包含 1-4 个内容块。

```ts
type StreamContentBlock = {
  type:
    | "plain_explanation"
    | "example"
    | "analogy"
    | "comparison_table"
    | "process_steps"
    | "pitfall"
    | "key_takeaway"
  title?: string
  content: string
  visual?: Visualization
}
```

内容块质量要求：

- 每个内容块只承担一个教学功能。
- 第一块优先建立学习动机或直觉，不直接堆定义。
- 中间块负责机制拆解、案例或对比。
- 最后一块必须给出明确 takeaway，告诉用户这一任务学到了什么。
- 如果这是节点最后一个任务，最后只做轻量收束，并提示用户进入下一节，不主动承接下一节知识。
- 复杂任务需要插入知识锚点，说明它和上一个任务的关系。
- 不确定有帮助的图表不要生成，避免为了可视化而可视化。

### 3.6 任务间用户操作

第一阶段不做练习题，也不做多分支反馈。任务间只保留“继续”。

| 操作 | 行为 |
|------|------|
| 继续 | 展示或生成下一个任务 |

后续扩展：

- 用户可以针对当前任务发问。
- 发问内容会进入当前节点上下文。
- 如果问题暴露出认知断点，系统可以调整本节点后续任务排布。
- “再讲一遍”“深入一点”不作为按钮单独实现，而是自然包含在用户发问能力里。

第一阶段只记录继续事件和节点完成事件，不基于它们更新画像。

### 3.7 生成链路调整

第一阶段建议把原来的 Cards + Questions 生成替换为 NodeTaskPlan 生成。

```text
Outline：基本保留
  ↓
TOC：基本保留，但节点描述要更强调 nodeGoal
  ↓
Node Task Plan：为单个节点生成任务计划
  ↓
Task Content：按任务流式生成讲解内容
  ↓
Final Task Prompt：最后一个任务提示用户进入下一节
```

第一阶段采用逐任务生成：

1. 课程目录生成后，立即预热第一个节点的 `NodeTaskPlan`。
2. 进入节点后，根据已有 `NodeTaskPlan` 单独请求第一个任务内容，并流式展示。
3. 上一个节点的第一个任务内容生成完毕后，开始预热下一个节点的 `NodeTaskPlan`。
4. 用户点击继续时，再单独请求下一个任务内容。
5. 已生成任务内容缓存到本地，返回时不重复请求。
6. 识别到最后一个任务时，在任务内容末尾提示进入下一节。

### 3.8 Prompt 设计重点

节点任务计划 Prompt 要强调：

- 先拆目标，再拆任务，不要直接写内容。
- 每个任务只解决一个学习目标。
- 任务之间必须有递进关系。
- 任务标题用动词开头。
- 只输出任务骨架，不输出任务正文。
- 每个任务只包含 `taskId`、`taskTitle`、`taskDescription`。
- 不生成练习题。
- 不生成选择题、填空题、测验题。
- 每个任务必须说明为什么排在这个位置。
- 每个节点必须生成 3-6 个任务。

任务内容 Prompt 要强调：

- 当前只生成一个任务的讲解内容。
- 讲解必须适合流式展示。
- 不要写成完整文章。
- 每个内容块短、清楚、有推进感。
- 普通任务结尾必须有一句自然的继续提示，例如“准备好了，我们继续看下一步。”
- 最后一个任务结尾不生成单独总结页，也不主动承接下一节知识，只提示用户进入下一节。
- 不要输出练习题。

### 3.9 第一阶段成功标准

| 指标 | 目标 |
|------|------|
| 节点内容完成率 | 用户愿意按任务读完整个节点 |
| 下一步点击率 | 用户在任务结束后愿意继续 |
| 节点生成等待时间 | 首个任务应尽快出现，避免等完整节点 |
| 主观质量 | 任务顺序自然，讲解不像碎片卡片拼接 |

第一阶段先用行为和主观体验判断课程质量，不急着用掌握度模型评估学习效果。

## 4. 课程生成链路

### 4.1 总链路

```text
用户输入主题
  ↓
需求解构 Intent Deconstruction
  ↓
课程蓝图 Course Blueprint
  ↓
目标簇章节 Goal-based TOC
  ↓
章节任务计划 Chapter Task Plan
  ↓
任务即时生成 Task Runtime Generation
  ↓
理解检查 Check-in
  ↓
画像更新 + 任务计划调整
```

### 4.2 需求解构

需求解构负责从用户原始输入中提取学习意图和边界。

| 字段 | 说明 |
|------|------|
| coreTopic | 核心学习主题 |
| intentType | 理论理解 / 技能掌握 / 问题解决 / 快速复习 |
| depthLevel | 入门 / 中级 / 高级 |
| confirmedKnowledge | 用户明确已会的内容 |
| excludedKnowledge | 用户明确要求跳过的内容 |
| targetScenario | 工作、考试、面试、项目、兴趣等应用场景 |
| ambiguity | 是否还需要澄清 |

意图类型影响后续课程框架：

| intentType | 默认课程倾向 |
|------------|--------------|
| 理论理解 | 渐进深入、探索推导、对比辨析 |
| 技能掌握 | 理论实践、步骤拆解、项目实战 |
| 问题解决 | 问题驱动、案例复盘、根因分析 |
| 快速复习 | 总分总、重点提炼、薄弱点强化 |

### 4.3 课程蓝图

课程蓝图定义整门课的定位和成功标准。

| 字段 | 说明 |
|------|------|
| learningDirection | 课程方向 |
| learningGoal | 学完后能做到什么 |
| learnerStartingPoint | 用户当前起点 |
| courseFrame | 课程组织框架 |
| mustCoverConcepts | 必须覆盖的薄弱概念 |
| skippableBasics | 可跳过基础 |
| riskConcepts | 易错或易混淆概念 |
| transferableBackground | 可用于类比的用户背景 |
| successCriteria | 整门课完成标准 |

蓝图质量要求：

- 禁止“全面掌握”“深入了解”等空泛目标。
- 目标必须可验证，能转成任务或题目。
- 已掌握内容不单独成章，只作为快速回顾或衔接。
- 风险概念必须在章节或任务中显式出现。

### 4.4 目标簇章节

V2 的章节结构应从“内容节点”升级为“目标簇节点”。

```ts
type GoalBasedChapter = {
  id: string
  title: string
  theme: string
  goalCluster: LearningGoal[]
  prerequisiteConcepts: ConceptRef[]
  targetConcepts: ConceptRef[]
  expectedOutput: string
  strategy: ChapterStrategy
  riskPoints: string[]
  masteryCriteria: string[]
}
```

章节生成时要回答四个问题：

1. 这一章解决用户的哪个认知断点？
2. 学完这一章后，用户能做出什么判断或动作？
3. 哪些概念必须真的掌握？
4. 哪些内容可以跳过、压缩或只在需要时补充？

## 5. 章节任务计划

### 5.1 任务计划定位

章节任务计划是 V2 的核心。它把一个章节目标簇拆成一组可执行、可验证、可动态调整的小任务。

```ts
type ChapterTaskPlan = {
  chapterId: string
  goals: LearningGoal[]
  tasks: LearningTask[]
  currentTaskId: string
  status: "not_started" | "in_progress" | "completed"
  adjustmentLog: AdjustmentLog[]
}
```

### 5.2 任务类型

| 类型 | 使用场景 |
|------|----------|
| concept_intro | 建立基础概念 |
| case_walkthrough | 用案例理解抽象概念 |
| comparison | 区分相似概念或方案 |
| guided_practice | 带用户完成一次操作或判断 |
| misconception_fix | 修复误区 |
| scenario_judgment | 在真实场景中做判断 |
| summary_review | 总结、巩固、复习 |
| deep_dive | 用户主动追问或表现出高级理解时插入 |

### 5.3 任务结构

```ts
type LearningTask = {
  id: string
  title: string
  targetGoals: string[]
  targetConcepts: ConceptRef[]
  taskType: LearningTaskType
  depth: "basic" | "intermediate" | "advanced"
  contentPlan: ContentBlockPlan[]
  checkIn: CheckInPlan
  successCriteria: string[]
  nextRules: TaskNextRules
}
```

任务标题要用动词开头，例如：

- 判断一个场景是否需要 RAG
- 对比 RAG 和 Fine-tuning 的适用边界
- 拆解 Agent 工具调用的完整链路
- 修正常见误区：Agent 不是“会自动思考的 Prompt”

### 5.4 内容块设计

每个任务包含 1-3 个内容块，避免重新变成长章节。

| 内容块类型 | 适用场景 |
|------------|----------|
| explanation | 概念解释 |
| example | 示例 |
| analogy | 类比 |
| comparison | 对比 |
| steps | 操作步骤 |
| visual | 流程图、表格、时间线等 |
| pitfall | 易错点 |
| takeaway | 小结 |

内容块生成原则：

- 每个内容块只服务一个小目标。
- 不确定可视化正确时不强行生成图。
- 术语密度由用户技术接受度和当前表现共同决定。
- 如果用户刚刚困惑，下一块内容必须换讲法。

### 5.5 Check-in 设计

每个任务至少有一个理解检查。

| 类型 | 用途 |
|------|------|
| single_choice | 快速确认概念理解 |
| multi_choice | 验证边界和多因素判断 |
| scenario_choice | 检查应用能力 |
| sequence_order | 检查流程理解 |
| self_explain | 让用户用自己的话解释 |
| micro_practice | 做一个小操作或小判断 |

Check-in 不只是出题，而是为了决定下一步。题目应绑定 `targetConcepts` 和 `successCriteria`，否则无法有效更新画像。

## 6. 动态调度规则

### 6.1 基础规则

| 用户信号 | 系统动作 |
|----------|----------|
| 答对且用时短 | 下一任务提速，减少铺垫 |
| 答对但用时长 | 标记为 fragile，后续轻复习 |
| 答错核心概念 | 插入 misconception_fix 任务 |
| 连续答错 | 降低深度，补前置概念 |
| 用户说“不懂” | 换解释方式，降低认知负荷 |
| 用户说“太简单” | 压缩解释，增加应用题或边界题 |
| 用户主动追问 | 插入 deep_dive 任务 |
| 用户跳过或退出 | 下次任务缩短，并优先回到主线 |

### 6.2 调整范围

动态调整优先级：

1. 调整当前任务的解释方式。
2. 插入一个补救或加速任务。
3. 重排本章节剩余任务。
4. 标记章节目标为需要后续复习。
5. 只有在严重前置缺口时，才建议用户先学更基础课程。

不要频繁重写整门课目录，否则用户会失去路径稳定感。

### 6.3 下一步决策

```ts
type TaskDecision =
  | { action: "continue"; nextTaskId: string }
  | { action: "insert_remediation"; task: LearningTask }
  | { action: "accelerate"; skippedTaskIds: string[]; nextTaskId: string }
  | { action: "switch_explanation"; currentTaskId: string; style: ExplanationStyle }
  | { action: "complete_chapter" }
```

每次决策都要记录 `adjustmentLog`，便于调试和后续画像精炼。

## 7. 用户画像构建策略

### 7.1 五层画像

V2 用户画像建议分为五层。

| 层级 | 说明 | 更新频率 |
|------|------|----------|
| Stable Profile | 目标岗位、工作经历、教育背景、类比经验 | 低 |
| Knowledge Profile | 概念掌握度、误区、遗忘曲线 | 高 |
| Learning Behavior Profile | 学习节奏、任务耐受、退出模式 | 中 |
| Explanation Preference | 偏好的解释方式 | 中 |
| Recovery Profile | 卡住后哪种补救最有效 | 中 |

### 7.2 Stable Profile

继续沿用显式画像：

| 字段 | 用途 |
|------|------|
| targetJob | 决定课程方向和场景选择 |
| workSummary | 判断用户已有经验 |
| educationSummary | 判断可用前置知识 |
| analogyExperiences | 生成类比 |
| valuePriorities | 决定内容侧重 |
| technicalLevel | 控制术语密度 |

要求：只提取事实，不做过度推测。

### 7.3 Knowledge Profile

继续沿用现有概念掌握度设计：

| 状态 | 条件 | 教学含义 |
|------|------|----------|
| mastered | 高掌握度且近期无错 | 可跳过或快速带过 |
| fragile | 有基本理解但不稳 | 需要轻复习或应用验证 |
| learning | 正在学习或有错误 | 需要主线教学 |
| unknown | 未接触 | 需要从前置概念开始 |

保留现有思想：

- 答错影响大于答对。
- 完成任务不等于掌握。
- 困惑信号会降低掌握判断。
- 掌握度需要随时间衰减。

### 7.4 Learning Behavior Profile

新增学习行为画像。

```ts
type LearningBehaviorProfile = {
  preferredTaskLength: "short" | "medium" | "long"
  pace: "slow" | "normal" | "fast"
  cognitiveLoadTolerance: "low" | "medium" | "high"
  dropOffPatterns: DropOffPattern[]
  checkInReliability: Record<CheckInType, number>
}
```

用途：

- 决定单个任务长度。
- 决定多久停顿一次。
- 决定是否适合公式、代码、抽象推导。
- 判断哪类题型最能测出真实理解。

### 7.5 Explanation Preference

解释偏好不应只升不降，而应具备时间衰减和反证机制。

```ts
type ExplanationPreference = {
  style: ExplanationStyle
  confidence: number
  evidenceCount: number
  lastConfirmedAt: string
  negativeEvidenceCount: number
  contexts: string[]
}
```

规则：

- 多次主动请求才提升置信度。
- 长期未出现则轻微衰减。
- 用户最近多次选择相反风格时降低旧偏好。
- 偏好要区分场景：技术概念可能喜欢步骤，商业概念可能喜欢案例。

### 7.6 Recovery Profile

Recovery Profile 记录用户卡住后，哪种补救方式最有效。

```ts
type RecoveryProfile = {
  conceptId?: string
  failurePattern: "misconception" | "missing_prerequisite" | "low_attention" | "too_abstract"
  effectiveInterventions: {
    style: "example" | "analogy" | "comparison" | "step_by_step" | "counterexample"
    successRate: number
    evidenceCount: number
  }[]
}
```

这是 V2 个性化的关键。一个好的学习系统不只是知道用户哪里不会，还要知道“怎么帮这个用户从不会到会”。

## 8. 记忆 Payload 设计

保留现有 Planning / Teaching / Chat Payload，并新增两个运行时 Payload。

| Payload | 使用阶段 | 内容 |
|---------|----------|------|
| Planning Payload | 蓝图、目录 | 用户起点、目标、已掌握、薄弱点、近期课程 |
| Chapter Planning Payload | 章节任务计划 | 本章目标、前置掌握度、风险概念、推荐策略 |
| Task Runtime Payload | 当前任务生成 | 当前任务、上一任务结果、偏好、认知负荷 |
| Check-in Evaluation Payload | 答题/反馈评估 | 用户答案、目标概念、成功标准、耗时、困惑 |
| Profile Update Payload | 画像更新 | 掌握度变化、偏好信号、补救效果、任务决策 |

新增 Payload 的目的不是扩大上下文，而是让每个阶段只拿自己需要的信息。

## 9. 迁移路径

### P0：节点任务流协议

把单节点内容协议从 `cards + questions` 改为 `NodeTaskPlan + streamed task content`。

第一阶段新增或调整：

- `nodeGoal`
- `tasks`
- `isFinalTask`

`tasks` 只包含任务骨架：

- `taskId`
- `taskTitle`
- `taskDescription`

任务内容由独立流式请求生成，不进入 `NodeTaskPlan`。

不再生成：

- `questions`
- `answer`
- `options`
- `correctAnswer`
- `questionType`

### P1：NodeTaskPlan 生成

新增单节点任务计划生成逻辑。TOC 阶段可以基本保留，但节点内容生成阶段改为：

```text
nodeInfo + blueprint + teaching constraints
  → NodeTaskPlan
```

第一版重点不是动态调度，而是确保任务拆解质量：

- 任务之间有递进关系。
- 每个任务只解决一个目标。
- 任务标题动词化。
- 每个节点 3-6 个任务。
- 不生成任务正文。

生成时机：

- 课程目录生成完成后，立即预热第一个节点的 `NodeTaskPlan`。
- 上一个节点的第一个任务内容生成完毕后，预热下一个节点的 `NodeTaskPlan`。
- 如果预热失败，不阻塞当前节点学习；用户进入下一个节点时再补生成。

### P2：流式任务学习页

学习页从：

```text
intro → card1 → card2 → questions → complete
```

改成：

```text
intro → task_content → user_continue → next_task → final_task_bridge → complete
```

学习页需要支持：

- 当前任务流式展示。
- 任务结束后暂停。
- 用户点击“继续”后进入下一任务。
- 只有“继续”一个任务间操作。
- 最后一个任务结束后直接标记节点完成。
- 最后一个任务内容末尾只提示进入下一节，不主动承接下一节内容。

### P3：任务内容逐个生成

将“生成整个节点内容”升级为“按任务生成内容”：

```text
进入节点：读取或生成 NodeTaskPlan
开始任务：单独流式生成当前任务内容
点击继续：单独流式生成下一个任务内容
最后任务：生成任务内容 + 进入下一节提示
```

已生成内容缓存到本地，避免回退时重复调用。

### P4：节点完成状态

节点结束时不再用练习题或单独总结页收束，而是在最后一个任务中完成轻量收束：

- 本节讲过的关键点。
- 用户现在应该能理解或判断什么。
- 提示用户进入下一节。

完成节点后暂时只记录进度，不更新新的画像字段。

### P5：任务问答入口

第二阶段优先做用户针对任务内容发问：

- 用户可对当前任务提问。
- 回答保留当前任务上下文。
- 如果问题暴露缺口，可影响后续任务排布。

### P6：画像升级

后续再接入：

- Learning Behavior Profile
- Explanation Preference 衰减机制
- Recovery Profile
- 基于任务反馈的掌握度更新

### P7：完整生成协议重构

当任务流体验验证有效后，再重构 prompt 和 Python Agent 服务：

- 需求解构 Agent
- 目标簇 TOC Agent
- 章节任务计划 Agent
- 任务即时生成 Agent

## 10. 推荐实施方案

建议采用“目标架构按 V2，落地节奏按渐进迁移”的方案。

不要一开始全盘重构课程生成。第一阶段先完成课程生成和学习流：

1. `NodeTaskPlan` 数据结构。
2. 单节点任务计划生成 Prompt。
3. 单任务流式内容生成 Prompt。
4. 学习页任务式推进体验。
5. 只有“继续”的任务间交互。
6. 最后任务中的本节收束和进入下一节提示。
7. 节点完成状态。

验证指标：

| 指标 | 说明 |
|------|------|
| 首任务出现时间 | 用户进入节点后多久看到第一段内容 |
| 下一步点击率 | 用户是否愿意顺着任务继续学 |
| 节点完成率 | 任务流是否提升节点完成 |
| 主观课程质量 | 任务顺序是否自然，内容是否像真正教学 |

如果这些指标变好，再继续做练习、画像和 Agent 拆分。

## 11. 已确认决策与待决策问题

已确认：

1. 第一版逐任务生成，生成过程直接展示给用户。
2. 第一版任务间只有“继续”按钮。
3. 用户针对任务发问、发问后调整后续任务排布，后续再做。
4. 不做单独总结页，最后一个任务末尾补 1-2 句收束和下一节引导。
5. 练习题彻底隐藏。未来如果恢复，也作为任务内容类型，而不是独立题卡。
6. 每个节点 3-6 个任务。
7. `NodeTaskPlan` 只包含任务骨架：`taskId`、`taskTitle`、`taskDescription`。
8. 第一个任务内容和 `NodeTaskPlan` 分开请求，任务内容必须流式展示。
9. 第一个节点的 `NodeTaskPlan` 在课程目录生成后立即预热；下一个节点的 `NodeTaskPlan` 在上一个节点第一个任务内容生成完毕后预热。
10. 最后一个任务不主动承接下一节内容，只提示用户进入下一节。

仍需实现前确认：

1. `NodeTaskPlan` 预热失败时，前端是否需要展示状态，还是静默重试？
2. 任务内容流式生成失败后，是允许重试当前任务，还是回退到本地兜底文案？
3. 用户退出节点再回来时，是否恢复到当前任务末尾，还是恢复到节点入口？
